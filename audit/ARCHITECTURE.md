# 영어 문장 전수 검수 — 설계

목표: 이 앱이 학습자에게 보여주는 **모든 영어 문자열**을 빠짐없이 뽑아,
미국식 영어 문법·용법에 어긋나는 것을 찾아낸다.

---

## 1. 왜 grep 으로는 안 되는가

앱의 영어 문장은 대부분 **저장돼 있지 않다.** `data.js` 는 동사 하나를
11개 시제·조동사 형태로 굴리고 거기에 의문사 5개를 곱해서 화면에서 만들어낸다.

```
Do you buy?  ←  FORMS.present.en({base:'buy'})   … 소스에 이 문자열은 없다
```

그래서 추출기는 데이터 모듈을 **실제로 실행한다** (`node:vm` 에 가짜 `window` 를
주입해 `data.js`/`patterns.js`/`roots.js` 를 그대로 돌린다). 카드 생성 함수
`buildDeck` · `buildPatternDeck` · `buildRootDeck` 를 모든 조합으로 호출해
화면에 뜨는 것과 같은 문자열을 얻는다. 데이터가 늘어나도 추출기는 그대로다.

## 3. 검수 단위 — 4,979개를 다 보지 않는다

생성 문장 2,112개의 문법적 적법성은 개별 문장이 아니라
**(의문사 × 시제형 × 동사종류)** 형태에서 결정된다. 동사는 슬롯일 뿐이다.
그래서 축을 둘로 나눈다.

```
A1 형태  241 템플릿      "{Q} do you {V}?" 가 성립하는 형태인가     → 문장 4,404개 커버
                        (의문 175 + 평서 33 + 부정 33)
A2 어휘    3 동사×형태군  목적어 없이 쓰이는 동사가 성립하는가       → 보조축
A3 결합   41 동사        동사 + 기본 목적어가 자연스러운 연어인가    → 보조축
B  문장  207 문장/구     교재 문장. 하나하나 봐야 한다
C  단어  367 단어        철자(미/영) · 형태소 분해 · 뜻
D  코드    1 문장        소스에 박힌 영어
──────────────────────────────────────────────────────────────
        860 단위  →  4,979개 전부 커버

동사를 21개 늘렸을 때 검수 단위는 오히려 줄었다(843 → 806).
새 동사가 **새 형태를 만들지 않기 때문**이다 — 형태는 (의문사 × 시제형 × 동사종류)
187개로 고정이고, 동사는 그 슬롯에 들어갈 뿐이다. 그래서 A1 판정 187건이
문장 2,112개든 3,432개든 그대로 덮는다. 동사마다 새로 봐야 하는 것은
목적어 결합(A3) 하나뿐이다.
```

A2 를 동사가 아니라 **동사 × 형태군**으로 쪼갠 이유: 목적어 생략 가능성이
형태마다 다르기 때문이다. `Do you buy?` 는 비문이지만 `Are you buying?` 은
문맥 생략으로 성립한다. 11개 시제형을 뒤에 오는 꼴로 3군(한정형·진행형·enjoy+-ing)
으로 묶었다.

두 축이 같은 문장을 겹쳐 보므로 **영향 범위는 합이 아니라 문장 id 합집합**으로 센다.
그래서 모든 검수 단위가 자기가 덮는 코퍼스 id 목록(`ids`)을 들고 다니고,
배치에는 `axis` 를 붙여 주축(코퍼스를 나눠 가짐)과 보조축(A2)을 구분한다.
review.mjs 는 주축 id 합집합이 코퍼스 크기와 같은지 매번 자체 검증한다.

## 4. 2단 검수

### 1차 — 기계 (`prescreen.mjs`)
문자열만 보고 판정되는 것. 판단이 필요 없다.

| 규칙 | 내용 |
|---|---|
| R1 | 영국식 철자 54종 (colour·centre·realise·travelled…) |
| R2 | 영국식 관용·전치사 (different to · in hospital · at the weekend…) |
| R3 | 연속 공백 · 구두점 앞 공백 · 둥근 따옴표 · 비ASCII |
| R4 | 완전한 문장의 첫 글자 대문자 · 종결부호 · 의문문 물음표 |
| R5 | 형태소를 이어 붙인 문자열이 표제어와 맞는지. 표제어가 그 문자열로 **시작**하면 접미사 생략(정상), 아니면 결합 실패(연결모음 누락·철자 변화 미반영) |
| R6 | 같은 영어인데 한국어 번역이 다른 중복 |
| R7 | 생성형 템플릿의 구조적 위험 (목적어 없는 타동사 · 목적격 who) |
| | ↳ 목적어를 주는 의문사는 what·who 뿐. 나머지 5단계는 전부 목적어가 없다 |
| R8 | 동사 사전의 `ing` 철자가 자음중복·묵음e 규칙과 맞는지 |
| R9 | 상태동사(know·like·want…)가 동사 사전에 들어왔는지 — 드릴이 전부 진행형으로 굴리므로 들어오면 "Are you knowing?" 이 된다 |

### 2차 — 판정 (`review.mjs` → `verdicts/`)
기계가 못 하는 것: **자연스러움**과 **미국 구어 여부**.
판정 4종으로만 쓴다. 애매하면 `confidence` 를 낮춘다.

| 판정 | 뜻 |
|---|---|
| `ok` | 미국식으로 정상 |
| `awkward` | 문법은 맞지만 원어민이 그렇게 말하지 않음 |
| `error` | 문법 오류 / 비문 |
| `uk` | 문법은 맞으나 영국식 |

`awkward` 와 `error` 를 섞지 않는 게 중요하다. 학습 교재에서
"틀린 문장"과 "안 쓰는 문장"은 대응이 다르다 — 전자는 고치고,
후자는 목적어를 붙이거나 문항을 바꾼다.

## 5. 실행

```bash
node audit/run.mjs
```

```
extract.mjs   → out/corpus.json · shapes.json · verbs.json · corpus.tsv
prescreen.mjs → out/prescreen.json · prescreen.md
review.mjs    → out/queue/<배치>.json · verdicts/<배치>.template.json
report.mjs    → REPORT.md
```

판정을 채울 때는 `verdicts/A1-형태.template.json` 를
`verdicts/A1-형태.json` 으로 복사해 `verdict` 필드를 채운 뒤
`node audit/run.mjs report`.

보고서는 판정이 낡았는지를 스스로 검사한다.
- **대상이 사라진 판정** — 판정 id 가 큐에 없다(단어를 교체하는 등 데이터가 바뀜).
- **재판정 안 된 판정** — id 는 같은데 문장이 바뀌었다. 판정할 때 박아 둔 `en` 과
  현재 `en` 을 대조한다. 이게 없으면 **이미 고친 것이 계속 결함으로 잡힌다.**

`REPORT.md` 는 결함보다 **커버리지를 먼저** 찍는다.
860단위 중 몇 개를 실제로 판정했는지가 표 맨 위에 나오고,
미판정이 남아 있으면 경고가 붙는다. "다 봤다"고 말할 수 있는 근거를
보고서 자신이 들고 있게 하기 위해서다.

## 6. 검수 결과가 데이터로 돌아간 곳

검수가 보고서로 끝나면 의미가 없다. 판정이 실제로 코드를 바꾼 지점:

| 판정 | data.js 반영 |
|---|---|
| 타동사에 목적어가 없다 (455문장 error) | `obj`·`objKo` 필드 + `makeCard` 의 슬롯 규칙 |
| 상태동사는 진행형이 안 된다 | R9 규칙 + VERBS 주석의 추가 규칙 ③ |
| `How do you have to ~?` 등 4조합이 어색하다 | `SKIP_COMBOS` — 그리드에서 제외 (How·Why 단계는 9장) |
| 어원 분해가 표제어를 못 만든다 (20건) | 연결모음 보강, 분해 불가였던 `voice` 는 `advocate` 로 교체 |

`SKIP_COMBOS` 때문에 단계별 카드 수가 11장으로 안 맞는다. 의도된 것이다 —
비는 자리를 채우려고 안 쓰는 문장을 넣는 것보다 낫다.

## 7. 데이터가 바뀌면

`data.js`/`patterns.js`/`roots.js` 를 고치면 `node audit/run.mjs` 를 다시 돌린다.
새로 생긴 단위는 `verdict: null` 로 남아 커버리지 표에 미판정으로 뜬다.
기존 판정은 id 로 붙으므로 다시 볼 필요가 없다.

id 규칙 — 데이터 순서가 바뀌어도 유지되도록 내용 기반으로 만든다.

```
gen:<동사>:<의문사>:<시제형>     shape:<의문사>|<시제형>|<동사종류>
pat:<0-패딩 인덱스>              verb:<동사>
root:<어근>:<단어>               code:<파일>:<n>
```

`pat:` 만 인덱스 기반이라 `patterns.js` 중간에 문장을 끼워 넣으면 어긋난다.
문장 추가는 배열 끝에 붙이는 것을 원칙으로 한다.

## 8. 알려진 미커버 축

전수 검수는 "모든 문장을 봤다"는 뜻이지, "모든 관점에서 봤다"는 뜻이 아니다.
지금 파이프라인이 **보지 않는** 축을 적어 둔다.

- **동사 × 시제형의 의미적 어색함.**
  A1 은 형태의 적법성만, A3 는 동사와 목적어의 결합만 본다.
  둘 다 통과해도 `Do you enjoy breaking a glass?` 처럼 의미가 이상한 조합이 남는다.
  동사 42개 × 형태군 3개 = 126단위를 더 봐야 완전해진다.
  지금은 눈에 띈 것만 A3 메모로 남겼다.

- **한국어 프롬프트의 정확성.**
  이 파이프라인은 영어를 검수한다. 한국어는 영어와 어긋날 때만 메모로 잡는다.
  예: 의문사 `where` 의 한국어가 `어디서` 로 고정이라 `go`·`sit` 에서
  `어디서 가니?`(→ 어디로), `어디서 앉니?`(→ 어디에) 가 나온다.

- **한국어 서술형·부정형의 파생 규칙.**
  동사마다 33개씩 손으로 적는 대신 어미 규칙으로 만든다(`koDeclOf`·`koNegOf`).
  54개 동사 전부를 훑어 이상 0건을 확인했지만, 새 동사를 넣을 때
  규칙이 안 통하면 이상한 한국어가 조용히 생길 수 있다.
  `koDec`·`koNeg` 는 반드시 손으로 적을 것.
